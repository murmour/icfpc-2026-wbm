# Folding IR: граф комнаты для прямоугольной укладки

Пакет `flow.folding` не подключён к существующим генераторам. Он задаёт
семантическую модель одной комнаты, которую затем можно укладывать в
прямоугольник любым алгоритмом: имитацией отжига, tabu search, CP-SAT или
ручной эвристикой.

## Построение графа из `.man`

`flow.folding.extract` строит модель непосредственно из готовой программы:

1. находит обычные прямоугольные комнаты;
2. находит `@` и подключённые к каждой стене концы труб;
3. восстанавливает направление и tie-rank портов;
4. обходит достижимый автомат состояний `(клетка, направление)`;
5. создаёт узлы на блокировках, ветвлениях, `Y`, `H` и слияниях;
6. сжимает промежуточные клетки в рёбра;
7. переносит арифметические инструкции в `EdgeAction`;
8. сохраняет исходные состояния каждого ребра в `EdgeTrace`.

Поклеточный автомат важен: одна физическая клетка, пересекаемая с разных
сторон, не обязана быть одной control-flow вершиной. Состояния различаются
направлением входа, поэтому обычное пересечение двух NOP-маршрутов не
превращается в ложный `JOIN`.

Если блокирующая команда одновременно является точкой слияния, узел получает
`allows_merge=True`. Его не приходится искусственно делить на два узла,
которые в исходнике занимали бы одну клетку.

Для просмотра:

```powershell
python tools\extract_folding_graph.py generated\matmul_pipeline.man --list
python tools\extract_folding_graph.py generated\matmul_pipeline.man --man-room 20
```

В текущем `matmul_pipeline.man` комната `20` — первый множитель. Она
преобразуется в 19 узлов и 21 ребро. В узлах остаются `r`, `s`, `d` и точки
слияния; стрелки исчезают, а `M`, `0`, `N`, `+`, `b`, `m`, `*` оказываются
на рёбрах. Для каждого узла и ребра текстовый вывод показывает исходную
координату и длину исходной трассы.

Трассировщик намеренно рассматривает все исходы ветвлений, не пытаясь
доказать значения `A` или `BP`. Поэтому комната с семантически невозможной,
но геометрически ведущей в стену ветвью пока отклоняется. Это отдельная
будущая задача абстрактной интерпретации, а не повод молча удалить ветвь.
`H` при этом уже является терминальным состоянием: клетки после него никогда
не обходятся.

## 1. Три уровня представления

### Семантические узлы

Узлом является событие, через которое нельзя без доказательства протащить
другую команду:

- старт `@` и остановка `H`;
- блокирующие и синхронизирующие операции `r`, `s`, `R`, `S`, `U`, `q`;
- условные повороты `d`, `a`, `X`, `x`;
- размножение `Y`;
- явная точка слияния маршрутов `JOIN`.

Для `r`, `s` и `q` узел содержит `NearestPort`. Это не фиксированная
координата, а область допустимых клеток: нужная труба должна выигрывать по
манхэттенскому расстоянию с официальным tie-break.

### Действия на рёбрах

Ребро содержит упорядоченную ленту `EdgeAction`. В неё разрешены только
неблокирующие преобразования регистров:

```text
 - * / % N & | ~ { } M W b m ] 0…9
```

Их можно двигать по маршруту и раздвигать NOP-клетками, но нельзя:

- менять их порядок;
- переносить через узел;
- ставить на поворот;
- давать чужому маршруту пройти через такую клетку.

Это важнее грубого деления на «важные» и «неважные» команды. Например, `M`
можно двигать только внутри ребра между двумя соседними блокирующими или
управляющими событиями.

Многоклеточные литералы пока намеренно не входят в ленту. Их ориентация
влияет на значение, поэтому позднее для них нужен отдельный footprint с
вариантами поворота.

### Синтезируемая геометрия

Стрелки на обычных изгибах и точки `.` отсутствуют в семантическом графе.
Роутер получает ортогональный путь и сам ставит абсолютную стрелку там, где
направление соседних шагов меняется.

Следовательно, служебный зигзаг можно полностью заменить другим маршрутом,
не переписывая граф.

## 2. Семантика рёбер и ветвлений

`Edge` соединяет именованный выход исходного узла со следующим узлом.
Выход задаёт правило направления:

- `straight`, `left`, `right` относительно входного направления;
- абсолютное направление;
- направление внутрь комнаты от заданного порта для моделирования `U`.

Стандартные наборы выходов проверяются:

| Инструкция | Выходы |
|---|---|
| `d` | `BP<=0`: прямо; `BP>0`: направо |
| `a` | `BP<=0`: прямо; `BP>0`: налево |
| `X` | `A<0`: налево; `A=0`: прямо; `A>0`: направо |
| `x` | младший бит 0: налево; младший бит 1: направо |
| `Y` | две одновременно создаваемые ветви: налево и направо |

Условие является типизированной частью `NodeExit`, а не только его
человекочитаемым именем. Поэтому невозможно случайно поменять местами
положительную и нулевую ветви `d`, сохранив ту же геометрию.

Обычный узел имеет ровно один вход. Если несколько маршрутов сходятся,
необходим явный `JOIN`; команда, уже стоящая в точке слияния исходной
программы, может быть merge-capable узлом. Это не даёт случайно спрятать
слияние внутри пересечения линий.

Циклы представлены обычными циклами графа через `JOIN`; self-loop запрещён,
чтобы у роутера всегда были две разные конечные точки ребра.

## 3. Кандидат укладки

Кандидат состоит из:

- координаты каждого узла;
- ортогонального пути каждого ребра, включая клетки обоих узлов;
- клеток, выбранных для каждой `EdgeAction`.

Текущий валидатор проверяет:

- попадание узлов в комнату и их placement domains;
- отсутствие наложения узлов;
- связность и ортогональность маршрутов;
- допустимую длину ребра;
- соответствие направлений семантике узла;
- одинаковое входное направление всех ветвей `JOIN`;
- порядок и непрерывность многосимвольных edge actions;
- отсутствие действий на поворотах;
- конфликты стрелок на пересечениях;
- прохождение маршрута через чужую команду или узел.

Пересечение двух прямых NOP-участков допустимо: пробел сохраняет направление
для обоих проходов. Стрелка или команда в точке пересечения делает его
конфликтным, если второй маршрут получит другую семантику.

## 4. Placer и энергия отжига

`evaluate_layout` возвращает:

- список hard violations;
- обычную и взвешенную длину маршрутов;
- число поворотов;
- скалярную энергию.

Пока используется:

```text
E =
    hard_penalty * violation_count
  + route_step_weight * Σ(edge_length * expected_traversals)
  + bend_weight * bend_count
```

`flow.folding.placer` реализует две фазы:

1. узлы независимо ставятся в случайные клетки своих domains, после чего
   дешёвый отжиг минимизирует лексикографическую цель
   `(hard violations, violation magnitude, weighted Manhattan)`;
2. для допустимых размещений рёбра сортируются по убыванию
   `expected_traversals` и последовательно прокладываются A*. Затем короткий
   route-aware отжиг двигает преимущественно концы непроложенных рёбер.

Положение узла дополнено его входным направлением. Оно необходимо, потому что
геометрия выходов `d`, `a`, `X`, `x`, `Y` и обычного продолжения определяется
направлением, с которого человечек вошёл в команду.

До маршрутизации используется:

```text
coarse =
    hard_count * dominant_penalty
  + graded_constraint_magnitude
  + Σ(expected_traversals * Manhattan) / scale
```

После маршрутизации:

```text
routed =
    unrouted_edge_weight * dominant_penalty
  + Σ(expected_traversals * actual_path_length)
  + bend_cost * bends
```

За нарушение `NearestPort` начисляется не только один hard violation, но и
разница расстояний до выбранной и требуемой трубы. Поэтому отжиг получает
градиент даже тогда, когда команда пока находится в области не той трубы.

A* фиксирует маршруты в порядке веса. Уже занятые пустые клетки разрешено
пересекать прямо и использовать для совместимого слияния. Стрелка может быть
переиспользована только если она задаёт требуемое направление; через чужой
`EdgeAction` проход запрещён. Действия ребра после трассировки размещаются на
свободных прямых участках в исходном порядке.

Запуск на первом multiplier-блоке:

```powershell
python tools\place_folding_graph.py generated\matmul_pipeline.man `
  --man-room 20 --seed 2 `
  --placement-iterations 5000 --routing-iterations 120
```

Для текущего графа из 19 узлов и 21 ребра этот бюджет на контрольном запуске
нашёл укладку без hard violations и проложил все рёбра. Результат пока
можно отрисовать и встроить в исходную программу:

```powershell
python tools\place_folding_graph.py generated\matmul_pipeline.man `
  --man-room 20 --seed 2 `
  --placement-iterations 5000 --routing-iterations 120 `
  --preview generated\matmul_multiplier_placed_room.man
```

`render_room_layout` ставит команды узлов, переносимые действия и стрелки на
поворотах; все посещаемые NOP-клетки отмечаются точками. `embed_graph_layouts`
заменяет внутренность одной или нескольких семантически одинаковых комнат,
не трогая стены и трубы.

Обратное извлечение preview множителя снова даёт 19 узлов и 21 ребро. Однако
это пока только локальная control-flow эквивалентность. Замена одного
множителя меняет порядок поступления результатов уже на `2×2`, поэтому
будущая глобальная проверка должна учитывать блокировки и относительные
времена труб.

## 5. Автоматическое профилирование весов

`expected_traversals=1` годится только до первого рабочего цикла. Динамический
профилировщик запускает исходную программу в неизменённом Go-эмуляторе и
считает успешные выходы из каждого семантического узла. Повторные тики
заблокированного `r` или `s` не считаются: ребро получает ровно один проход,
когда человечек действительно покидает исходный узел.

Профиль тестов — JSON:

```json
{
  "cases": [
    {
      "name": "2x2",
      "inputs": [2, 2, 2, 1, 2, 3, 4, 5, 6, 7, 8],
      "output_count": 4,
      "weight": 1
    }
  ]
}
```

Команда:

```powershell
python tools\profile_folding_weights.py `
  generated\matmul_pipeline.man --man-room 20 `
  --cases profiles\matmul_small.json --all-matching `
  --output generated\matmul_multiplier_weights.json
```

`--all-matching` агрегирует счётчики структурно одинаковых комнат. При этом
арифметика на рёбрах может отличаться: у Matrix-воркеров это номер столбца,
но управляющие узлы и имена соответствующих рёбер совпадают. Поэтому один
профиль автоматически суммирует активные и inactive-drain проходы всех 16
воркеров.

Полученные веса можно передать placer:

```powershell
python tools\place_folding_graph.py generated\matmul_pipeline.man `
  --man-room 20 --weights generated\matmul_multiplier_weights.json
```

Или измерить их в том же запуске:

```powershell
python tools\place_folding_graph.py generated\matmul_pipeline.man `
  --man-room 20 --all-matching `
  --profile-cases profiles\matmul_small.json `
  --profile-output generated\matmul_multiplier_weights.json
```

Среднее зависит от набора профильных входов. Для серверной метрики профиль
должен приближать распределение размеров серверных тестов; задержки труб
влияют на момент остановки, но заблокированные тики не увеличивают счётчик
проходов ребра.

Взвешенная длина — только дешёвая аппроксимация. Изменение пути может менять
блокировки труб и синхронизацию комнат, как уже происходило в Matrix
Multiplication. Поэтому окончательная функция второй фазы должна периодически
запускать эмулятор на профиле входов или использовать отдельную
событийно-временную модель.

Для этого у ребра уже есть:

- `expected_traversals`;
- `minimum_steps` / `maximum_steps`;
- строковый `timing_class` для будущих относительных ограничений.

## 6. Состояние и ходы annealer

Текущее состояние поиска:

```text
(позиции узлов, входные направления, маршруты рёбер, позиции edge actions)
```

Реализованные ходы:

- сдвинуть один свободный узел;
- поменять местами два узла;
- выбрать другую допустимую клетку портового узла;
- изменить входное направление узла;
- после каждого route-aware хода полностью перестроить рёбра A*.

Локальный rip-up/reroute и инкрементальное обновление стоимости пока не
реализованы. Полная перетрассировка достаточно быстра для небольших комнат,
но станет следующим узким местом на более крупных графах.

## 7. Что пока не формализовано

- многоклеточные и направленно-зависимые литералы;
- доказательство эквивалентности состояний регистров в `JOIN`;
- столкновения нескольких человечков после `Y`;
- точная модель блокировок труб;
- абстрактная интерпретация регистров для отбрасывания невозможных ветвей;
- глобальная временная проверка синтезированной комнаты в окружении соседей.

Первый пример — `multiplier_steady_state_graph()`. В нём четыре обращения к
трубам являются узлами, а `M` и `*` лежат на рёбрах.
